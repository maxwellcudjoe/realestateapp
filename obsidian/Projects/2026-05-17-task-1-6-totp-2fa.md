# Task 1.6 — TOTP Two-Factor Authentication

Closes gap **X1** (no 2FA on a financial platform — table-stakes). Adds opt-in
TOTP enrolment with QR + manual key, 10 single-use recovery codes, and a
two-step login flow when 2FA is active.

## Schema

```prisma
model User {
  // ...existing
  totpSecret      String?   @db.NVarChar(255)
  totpEnabledAt   DateTime?
  // ...
  recoveryCodes   RecoveryCode[]
}

model RecoveryCode {
  id        String    @id @default(cuid())
  userId    String
  user      User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  codeHash  String    @db.NVarChar(255)
  usedAt    DateTime?
  createdAt DateTime  @default(now())

  @@index([userId])
}
```

Recovery codes are stored as **bcrypt hashes** of `XXXXX-XXXXX` strings. Plain
codes are shown to the user exactly once (after enrolment or regeneration).

## Library

`src/lib/totp.ts` — uses `otplib@13` (functional async API) and `qrcode`:
- `generateTotpSecret()` — base32 secret
- `totpKeyUri(email, secret)` / `totpQrDataUrl(email, secret)` — provisioning URI + PNG data URL
- `verifyTotpCode(secret, code)` — async, ±30s tolerance for clock drift
- `generateRecoveryCodes(n=10)` — returns `{plain, hashed}` pair
- `findMatchingRecoveryCode(candidate, rows)` — bcrypt compare loop, case-insensitive

## API

| Route | Purpose |
|---|---|
| `POST /api/portal/security/totp/enroll` | Generates pending secret, returns QR + manual key |
| `POST /api/portal/security/totp/confirm` | Verifies user typed a real code; activates 2FA; returns 10 recovery codes (shown once) |
| `POST /api/portal/security/totp/disable` | Requires password + (TOTP code OR recovery code); clears secret and codes |
| `POST /api/portal/security/totp/recovery-codes` | Regenerates 10 codes (requires fresh TOTP code) |
| `POST /api/auth/login-challenge` | Stateless probe — does the user need TOTP? Reuses lockout + rate-limit. Returns `{needsTotp}` only when credentials valid; otherwise always `false` (no enumeration) |

## Auth flow (gate)

`src/lib/auth.ts` `authorize()`:
1. Lockout check (X2)
2. Email + password (R3)
3. Email verified (R1)
4. **NEW** — if `user.totpEnabledAt`:
   - No code → log `totp-required`, reject
   - Code matches TOTP secret → proceed
   - Code matches an unused recovery code (bcrypt compare) → mark used, log `recovery-code`, proceed
   - Otherwise → log `bad-totp`, reject

## UX

### Login page (2-step)
1. User enters email + password → form submit
2. `/api/auth/login-challenge` fires. If `needsTotp: true`, the password field locks and a "Two-Factor Code" input appears with `autoComplete="one-time-code"` and autofocus
3. User enters 6-digit code (or recovery code) → re-submit → NextAuth `signIn` with all three fields

### `/portal/security`
- New "Two-Factor Authentication" section (above existing activity table)
- Idle state: "Enable 2FA" button
- Enrol flow: shows QR + manual key + 6-digit confirm input
- Post-confirm: displays the 10 recovery codes in a gold-bordered grid, "I've saved them" button
- Enabled state: shows enable date + "Disable 2FA" link (requires password + code to disable)

## Security properties

- Recovery codes are **bcrypt-hashed** — DB compromise doesn't expose them
- Recovery codes are **single-use** — burned on consumption
- TOTP secret is wiped from DB on disable (not just `totpEnabledAt = null`)
- Disable requires both password and a current code (or recovery code) — stops a hijacked session from removing 2FA
- Login challenge probe is rate-limited (10/15min/IP) and respects the same lockout as sign-in
- Login challenge always returns `needsTotp: false` for wrong credentials → no account enumeration
